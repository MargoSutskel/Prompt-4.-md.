| **Процесс и контекст использования** | • Артефакт используется в рамках процесса **генерации проектной документации** с помощью LLM-модели (DeepSeek). • Применяется на этапе **предпроектного анализа и детального проектирования** — от бизнес-требований до API-контрактов. • Создаётся системным аналитиком или архитектором, владеющим методами промпт-инжиниринга. |
| **Цель создания**                    | • Решает задачу **автоматизации создания комплекта согласованных артефактов** для финтех-проекта. • Обеспечивает **последовательную генерацию** документов, где каждый следующий артефакт строится на основе предыдущего. • Гарантирует **согласованность требований** между BRD, Sequence-диаграммой, ER-диаграммой и OpenAPI-спецификацией. • Снижает **трудозатраты** на подготовку документации и уменьшает риск человеческих ошибок. |
| **Что становится определено**        | • Зафиксирована **система из 4 промптов** (BRD → Sequence → ER → OAS) с чёткими ролями, форматами вывода и контекстными ограничениями. • Определены **цепочки передачи контекста** между промптами для обеспечения согласованности. • Зафиксированы **few-shot примеры** для каждого типа артефакта. • Определены **критерии валидации** каждого артефакта (смысловая согласованность, успешная валидация OAS). • Зафиксирован **формат хранения** результатов (Markdown, PlantUML, Mermaid, OpenAPI YAML/JSON). |
| **Пользователи артефакта**           | • **Системные аналитики** — используют промпты для генерации документации. • **Архитекторы** — используют для проверки согласованности артефактов. • **Разработчики** — используют сгенерированные артефакты для реализации. • **QA-инженеры** — используют для создания тестовых сценариев. • **Новые члены команды** — используют как примеры для обучения промпт-инжинирингу. |
| **Использование в дальнейшем**       | • После создания промптов становится возможной **быстрая генерация документации** для новых проектов. • Появляется **шаблон для тиражирования** на другие финтех-проекты. • Становится возможной **автоматическая валидация** OAS через Python-скрипты. • Документ используется для **обучения команды** работе с LLM. • Служит **основой для CI/CD-пайплайна** генерации документации. |
| **Последствия отсутствия**           | • Без промптов каждый аналитик будет **писать документацию вручную** → высокие трудозатраты и риск ошибок. • **Нарушится согласованность** между BRD, Sequence, ER и OAS. • **Замедлится онбординг** новых проектов. • **Невозможно будет автоматизировать** генерацию документации. • **Потеряется экспертиза** промпт-инжиниринга внутри команды. |

## Prompt 1: Генерация BRD-спецификации

### Роль

Ты — **продуктовый аналитик** с 10-летним опытом в финтех-проектах.

### Контекст

Проект: **«Платформа обработки платёжных поручений юридических лиц»**.
Домен: корпоративные платежи, РКО, комплаенс, интеграция с АБС.

### Задача

Разработай **BRD-спецификацию** (Business Requirements Document) для ключевого сценария: обработка платёжного поручения юридического лица от приёма до исполнения.

### Формат вывода

- **Markdown**
- Структура: бизнес-контекст, стейкхолдеры, бизнес-цели (SMART), границы (In/Out of Scope), функциональные требования, бизнес-процессы (AS-IS и TO-BE), ограничения, риски.
- Таблицы для структурированных данных.
- Не использовать техническую детализацию (API, БД — это для следующих этапов).

### Контекстные ограничения

- **Максимальная сумма платежа:** 100 000 000 руб.

- **Валюты:** только RUB (для MVP).

- **Типы комиссий:** фиксированная, процентная.

- **Статусы платежа:** DRAFT, VALIDATED, VALIDATION_FAILED, COMPLIANCE_PASSED, COMPLIANCE_BLOCKED, LIMITS_CONFIRMED, LIMITS_EXCEEDED, READY_TO_SEND, EXECUTED, EXECUTION_FAILED, REJECTED.

- **Регуляторика:** 115-ФЗ, 152-ФЗ, положения ЦБ РФ.

  ### Few-shot пример (фрагмент)

  markdown

  ```
  ## 1. Бизнес-контекст
  
  ### 1.1. Текущая проблема
  Обработка платёжных поручений юридических лиц осуществляется в монолитной системе с ручными проверками, что приводит к задержкам до 20 минут и ошибкам в 15% случаев.
  
  ### 1.2. Бизнес-цели (SMART)
  | № | Цель | Метрика | Текущее | Целевое | Срок |
  |---|------|---------|---------|---------|------|
  | 1 | Ускорить обработку | Время обработки | 20 мин | ≤ 30 сек | 6 мес |
  | 2 | Снизить ошибки | % ошибок | 15% | 0% | 6 мес |
  | 3 | Автоматизировать комплаенс | % автоматизации | 80% | 100% | 3 мес |
  ```

  ## 1. Бизнес-контекст

  ### 1.1. Текущая проблема

  Обработка платёжных поручений юридических лиц осуществляется в монолитной системе с ручными проверками, что приводит к задержкам до 20 минут и ошибкам в 15% случаев.

  ### 1.2. Бизнес-цели (SMART)

  | №    | Цель                       | Метрика         | Текущее | Целевое  | Срок  |
  | :--- | :------------------------- | :-------------- | :------ | :------- | :---- |
  | 1    | Ускорить обработку         | Время обработки | 20 мин  | ≤ 30 сек | 6 мес |
  | 2    | Снизить ошибки             | % ошибок        | 15%     | 0%       | 6 мес |
  | 3    | Автоматизировать комплаенс | % автоматизации | 80%     | 100%     | 3 мес |

  ------

  ## 2. Анализ целей
  
  ### 2.1. Декомпозиция цели №1: Ускорение обработки (20 мин → ≤ 30 сек)

  **Ключевые проблемы текущего процесса:**

  - Монолитная архитектура → все проверки выполняются последовательно в одном процессе
  - Ручные проверки → оператор вручную сверяет реквизиты, подписи, лимиты
  - Отсутствие асинхронности → система блокируется на время проверок
  
  **Что необходимо для достижения:**
  
  1. Выделение процесса обработки платёжного поручения в отдельный сервис (микросервисная архитектура)
  2. Автоматизация типовых проверок (формат, реквизиты, лимиты, дубли)
  3. Параллельное выполнение независимых проверок (комплаенс, антифрод, лимиты)
  4. Предварительная валидация на стороне клиента (API-контракт)
  5. Кэширование справочных данных (БИК, счета, контрагенты)
  
  **Ожидаемый эффект:**
  
  - Время обработки: 20 мин → 10–30 сек
  - Пропускная способность: рост в 40–120 раз
  
  ------
  
  ### 2.2. Декомпозиция цели №2: Снижение ошибок (15% → 0%)
  
  **Ключевые проблемы:**
  
  - Человеческий фактор при ручном вводе и проверке
  - Отсутствие сквозной валидации данных
  - Нет автоматической сверки с внешними источниками
  
  **Что необходимо для достижения:**
  
  1. Формализация всех правил проверки (бизнес-правила → исполняемый код)
  2. Валидация на входе (структурная, семантическая, бизнес-логика)
  3. Автоматическая сверка с ЕГРЮЛ/ЕГРИП, справочником БИК, лимитами
  4. Контроль дублей и идемпотентности
  5. Логирование и трассировка каждой проверки
  6. Постепенный вывод ручных операций (сначала — контроль, потом — полная автоматизация)

  **Ожидаемый эффект:**

  - Ошибки: 15% → 0% (при условии полной автоматизации)
  - Снижение операционных рисков
  
  ------
  
  ### 2.3. Декомпозиция цели №3: Автоматизация комплаенса (80% → 100%)
  
  **Ключевые проблемы:**
  
  - Часть проверок выполняется вручную (санкционные списки, ПОД/ФТ, 115-ФЗ)
  - Нет единого движка правил комплаенса
  - Отсутствие автоматического обновления списков

  **Что необходимо для достижения:**

  1. Внедрение движка бизнес-правил (BRMS) для комплаенс-проверок
  2. Интеграция с актуальными источниками санкционных списков
  3. Автоматическая проверка по 115-ФЗ, 173-ФЗ, санкциям ЦБ
  4. Настраиваемые правила без изменения кода
  5. Аудит и отчётность по каждой проверке
  
  **Ожидаемый эффект:**
  
  - Автоматизация комплаенса: 80% → 100%
  - Срок: 3 мес (быстрее, чем цели №1 и №2)
  
  ------
  
  ## 3. Связь целей с архитектурой
  
  | Цель               | Архитектурное решение                                        |
  | :----------------- | :----------------------------------------------------------- |
  | №1 Ускорение       | Микросервис «Платёжный процессинг», асинхронная обработка, параллельные проверки |
  | №2 Снижение ошибок | Сервис валидации, идемпотентность, трассировка, автоматическая сверка |
  | №3 Комплаенс       | BRMS, интеграция с внешними списками, автоматический аудит   |
  
  ------
  
  ## 4. Риски и допущения
  
  **Риски:**
  
  - Сопротивление бизнеса при переходе на новую систему
  - Задержки интеграции с внешними системами (ЦБ, ЕГРЮЛ)
  - Недостаточная производительность при пиковых нагрузках
  - Юридические ограничения на полную автоматизацию (требование ручной подписи)
  
  **Допущения:**
  
  - Внешние API (ЕГРЮЛ, санкционные списки) доступны и стабильны
  - Бизнес готов к изменению процесса
  - 0% ошибок достижимо при полной автоматизации и отсутствии сбоев

  ## Prompt 2: Генерация Sequence-диаграммы
  
  ### Роль
  
  Ты — **системный архитектор** с опытом проектирования микросервисных платформ.
  
  ### Контекст
  
  **Входные данные:** BRD-спецификация (из Prompt 1).
  
  **Архитектура проекта:**
  
  - Микросервисы: API Gateway, IAM, Payment Orchestrator, Validator, Compliance, Limits, АБС-адаптер, Notification, Audit, Reference.
  - Брокер: Kafka.
  - Внешние системы: ДБО, АБС, шлюзы уведомлений.
  
  ### Задача
  
  Построй **UML Sequence Diagram** для сквозного сценария обработки платёжного поручения, включая:
  
  1. Основной сценарий (успешный платёж).
  2. Альтернативный сценарий (комплаенс-блокировка → ручное решение).
  3. Сценарий сбоя (недоступность АБС → ретраи → итоговый статус).
  
  ### Формат вывода
  
  - **PlantUML** (для последующей визуализации).
  - Указать синхронные и асинхронные взаимодействия.
  - Указать передаваемые данные (DTO, события, команды).
  - Указать изменения статуса платежа в ключевых точках.
  
  ### Контекстные ограничения
  
  - Использовать **только те компоненты**, которые зафиксированы в C4-архитектуре.
  - Не описывать внутреннюю реализацию сервисов.
  - Соблюдать статусную модель из BRD.
  
  ### Few-shot пример (фрагмент)
  
  plantuml
  
  ```
  @startuml
  actor "Клиент" as Client
  participant "API Gateway" as APIGateway
  participant "Payment Orchestrator" as Orchestrator
  participant "Kafka" as Kafka
  participant "Validator" as Validator
  
  Client -> APIGateway: 1. POST /payments
  APIGateway -> Orchestrator: 2. POST /payments
  Orchestrator -> Orchestrator: 3. Проверка идемпотентности
  Orchestrator -> Kafka: 4. PaymentCreated
  Kafka -> Validator: 5. PaymentCreated
  Validator -> Kafka: 6. PaymentValidated
  @enduml
  ```

  ## Prompt 3: Генерация ER-диаграммы
  
  ### Роль
  
  Ты — **DBA (Database Administrator)** с опытом проектирования БД для финтех-систем.
  
  ### Контекст
  
  **Входные данные:**
  
  - BRD-спецификация (из Prompt 1).
  - Sequence-диаграмма (из Prompt 2).
  
  **Зона ответственности:** Только данные сервиса **Payment Orchestrator**.
  
  ### Задача
  
  Спроектируй **ER-диаграмму** для сервиса Payment Orchestrator, которая позволяет:
  
  1. Хранить платёжное поручение и его текущий статус.
  2. Восстанавливать историю изменения статусов.
  3. Защищаться от повторной регистрации одного и того же поручения.
  4. Хранить результаты проверок и ссылки на внешние операции.
  5. Связывать запись платежа с событиями и идентификаторами трассировки.
  
  ### Формат вывода
  
  - **PlantUML** (основной вариант) или **Mermaid** (альтернативный).
  - Для каждой сущности: назначение, атрибуты, PK, FK, обязательность, уникальные ограничения, индексы.
  - Для связей: тип и кардинальность (1:1, 1:N, M:N).
  
  ### Контекстные ограничения
  
  - Не дублировать данные других сервисов (Compliance, Limits, ABS Interaction, Reference).
  - Если хранится ссылка на внешний результат — отражать как ссылку или проекцию.
  - Соблюдать статусную модель из BRD.
  
  ### Few-shot пример (фрагмент)

  plantuml

  ```
  @startuml
  entity "payments" as payments {
    * payment_id : UUID <<PK>>
    --
    * external_payment_id : VARCHAR(50) <<UK>>
    * status : VARCHAR(30)
    * amount : DECIMAL(18,2)
    * created_at : TIMESTAMP
  }
  
  entity "payment_status_history" as history {
    * history_id : BIGSERIAL <<PK>>
    --
    * payment_id : UUID <<FK>>
    * status : VARCHAR(30)
    * created_at : TIMESTAMP
  }
  
  payments ||--o{ history : "имеет историю"
  @enduml
  ```

  ## Prompt 4: Генерация OpenAPI Specification (OAS)
  
  ### Роль
  
  Ты — **интегратор** с опытом проектирования REST API для финтех-систем.
  
  ### Контекст
  
  **Входные данные:**
  
  - BRD-спецификация (из Prompt 1).
  - Sequence-диаграмма (из Prompt 2).
  - ER-диаграмма (из Prompt 3).
  
  **Зона ответственности:** API сервиса **Payment Orchestrator** (через API Gateway).
  
  ### Задача
  
  Разработай **OpenAPI 3.0-спецификацию** для сервиса Payment Orchestrator, покрывающую:
  
  1. Приём платёжного поручения (`POST /payments`).
  2. Получение статуса платежа (`GET /payments/{paymentId}`).
  3. Обработку повторной отправки (идемпотентность через `X-Request-ID`).
  
  ### Формат вывода
  
  - **YAML** (основной) или **JSON** (альтернативный).
  - Для каждого эндпоинта: HTTP-метод, URL, назначение, параметры, структура ответа, коды ответов (2xx, 4xx, 5xx), структура ошибки, примеры.
  - Отдельно отразить: идемпотентность, различие между приёмом и исполнением, авторизацию, кэширование.
  
  ### Контекстные ограничения
  
  - Не добавлять CRUD-операции, если они не требуются (обосновать).
  - Использовать статусы из BRD.
